## 1. 裁决一：限流冷却期内回 429 + `Retry-After`

### 问题

T6 落地后发现：熔断/冷却期间，候选被跳过 → 网关回 **502 `upstream_error`（"没有可用候选：全部候选被跳过或熔断中"）**。

但冷却期的**真实原因是上游限流**。客户端拿到 502 时：

- 不知道这是"等一会儿就好"，会当成"上游坏了"而放弃或乱重试；
- 拿不到任何"多久后再试"的信号。

### 方案

区分熔断打开的**原因**，冷却期内给出对应的语义：

| 打开原因 | 冷却期内回什么 | 响应头 |
|---|---|---|
| 上游限流（429） | **429 `rate_limit_error`** | `Retry-After: <剩余冷却秒数>` |
| 连续失败（5xx / 网络错误） | 502 `upstream_error`（信息含"熔断"） | — |

`Retry-After` **只走响应头，不进错误体**——02 §4.4 的错误体字段表保持不变（字段表没有它，硬塞会破坏既有错误体的逐字节一致性）。

### 取舍

- **错误体不变** vs **把 `retry_after` 塞进 JSON**：选前者。统一错误体的字段表是 02 §4.4 的契约，HTTP 头是放"重试时机"的标准位置（RFC 9110），不需要新造字段。
- **429 vs 503**：选 429。客户端/harness 对 429 的处理惯例（带 `Retry-After`）已经存在，换 503 等于要客户端学新约定。

### 落点

02 §4.4（回填口径表）；实现见 `gateway/errors.rs`（`with_retry_after` → `Retry-After` 响应头）与 `gateway/fallback.rs`（按打开原因分流）。

## 2. 裁决二：熔断状态落库 + UI 展示

### 问题

02 §2.3 原本写"冷却状态存内存，重启即清零（不做持久化，避免误伤）"。两个代价：

1. **限流保护被绕过**：重启网关就能立刻重试被 429 的上游——限流的意义就是让上游喘口气。
2. **用户看不到**：渠道正在冷却时，UI 上一片空白，用户只能猜"为什么请求慢了/失败了"。

### 方案

**持久化**：新增 `circuit_state` 表（02 §9），非 closed 的熔断状态**写穿**落库：

| 状态 | 落库行为 |
|---|---|
| open / half_open | upsert 一行（状态、原因、失败次数、冷却截止） |
| closed | 删除该行 |
| 未达阈值的连续失败（1~2 次） | 不落库（仍是 closed） |

**启动恢复**：应用启动时读回落库行，恢复熔断状态——重启不再绕过限流。

**误伤评估**：冷却窗口本身很短（失败熔断 60s、429 冷却上限 60s），持久化不会造成长期误伤；"避免误伤"的初衷由**短窗口**保证，而不是靠"重启清零"。

**UI 展示**：新增"熔断状态"面板（`circuit_status` IPC），列出当前处于熔断/冷却的 `(渠道, 上游模型)`：状态、原因、剩余秒数，每 5s 自动刷新。

### 取舍

| 选择 | 理由 |
|---|---|
| 写穿（状态一变即写），不做定时快照 | 快照会有"内存状态与库里不一致"的窗口；写穿无额外一致性成本 |
| 只落库非 closed | 表里天然只反映"正在冷却的渠道"，不会无限增长；回到正常即自动清理 |
| 落库失败只记日志，不影响请求 | 熔断状态丢失只是重新计数，不能让请求失败 |
| 失败计数不落库 | 未达阈值的 1~2 次失败重启后清零——本来就不该拦请求，落库没有价值 |
| UI 读运行中的熔断器（不是查库） | 库是持久化副本，运行时真相在内存；查库会滞后于内存 |
| 不做"手动解除熔断"按钮 | 本次裁决只要求展示；手动解除属 T9 UI 第一轮的范围，可后续加 |

### 落点

02 §2.3 / §9；实现见 `store/schema.rs`（DDL）、`store/migrations.rs`（v5 迁移）、`gateway/circuit.rs`（快照 + 持久化 trait）、`gateway/circuit_store.rs`（落库实现）、`commands/circuit.rs`（IPC）、`src/CircuitPanel.tsx`（前端）。

- **账号级熔断**：粒度仍是 `(channel_id, upstream_model)`，不是 `(channel, account)`——账号池尚未落地（T8/T9）。
