## 1. 裁决一：限流冷却期内回 429 + `Retry-After`

### 问题

T6 落地后发现：熔断/冷却期间，候选被跳过 → 网关回 **502 `upstream_error`（"没有可用候选：全部候选被跳过或熔断中"）**。

但冷却期的**真实原因是上游限流**。客户端拿到 502 时：

- 不知道这是"等一会儿就好"，会当成"上游坏了"而放弃或乱重试；
- 拿不到任何"多久后再试"的信号。

### 方案

区分熔断打开的**原因**，冷却期内给出对应的语义：

| 打开原因 | 冷却期内回什么 | 响应头 |
|---|---|---|
| 上游限流（429） | **429 `rate_limit_error`** | `Retry-After: <剩余冷却秒数>` |
| 连续失败（5xx / 网络错误） | 502 `upstream_error`（信息含"熔断"） | — |

`Retry-After` **只走响应头，不进错误体**——02 §4.4 的错误体字段表保持不变（字段表没有它，硬塞会破坏既有错误体的逐字节一致性）。

### 取舍

- **错误体不变** vs **把 `retry_after` 塞进 JSON**：选前者。统一错误体的字段表是 02 §4.4 的契约，HTTP 头是放"重试时机"的标准位置（RFC 9110），不需要新造字段。
- **429 vs 503**：选 429。客户端/harness 对 429 的处理惯例（带 `Retry-After`）已经存在，换 503 等于要客户端学新约定。

### 落点

02 §4.4（回填口径表）；实现见 `gateway/errors.rs`（`with_retry_after` → `Retry-After` 响应头）与 `gateway/fallback.rs`（按打开原因分流）。

## 2. 裁决二：熔断状态落库 + UI 展示

### 问题

02 §2.3 原本写"冷却状态存内存，重启即清零（不做持久化，避免误伤）"。两个代价：

1. **限流保护被绕过**：重启网关就能立刻重试被 429 的上游——限流的意义就是让上游喘口气。
2. **用户看不到**：渠道正在冷却时，UI 上一片空白，用户只能猜"为什么请求慢了/失败了"。

### 方案

**持久化**：新增 `circuit_state` 表（02 §9），非 closed 的熔断状态**写穿**落库：

| 状态 | 落库行为 |
|---|---|
| open / half_open | upsert 一行（状态、原因、失败次数、冷却截止） |
| closed | 删除该行 |
| 未达阈值的连续失败（1~2 次） | 不落库（仍是 closed） |

**启动恢复**：应用启动时读回落库行，恢复熔断状态——重启不再绕过限流。

**误伤评估**：冷却窗口本身很短（失败熔断 60s、429 冷却上限 60s），持久化不会造成长期误伤；"避免误伤"的初衷由**短窗口**保证，而不是靠"重启清零"。

**UI 展示**：新增"熔断状态"面板（`circuit_status` IPC），列出当前处于熔断/冷却的 `(渠道, 上游模型)`：状态、原因、剩余秒数，每 5s 自动刷新。

### 取舍

| 选择 | 理由 |
|---|---|
| 写穿（状态一变即写），不做定时快照 | 快照会有"内存状态与库里不一致"的窗口；写穿无额外一致性成本 |
| 只落库非 closed | 表里天然只反映"正在冷却的渠道"，不会无限增长；回到正常即自动清理 |
| 落库失败只记日志，不影响请求 | 熔断状态丢失只是重新计数，不能让请求失败 |
| 失败计数不落库 | 未达阈值的 1~2 次失败重启后清零——本来就不该拦请求，落库没有价值 |
| UI 读运行中的熔断器（不是查库） | 库是持久化副本，运行时真相在内存；查库会滞后于内存 |
| 不做"手动解除熔断"按钮 | 本次裁决只要求展示；手动解除属 T9 UI 第一轮的范围，可后续加 |

### 落点

02 §2.3 / §9；实现见 `store/schema.rs`（DDL）、`store/migrations.rs`（v5 迁移）、`gateway/circuit.rs`（快照 + 持久化 trait）、`gateway/circuit_store.rs`（落库实现）、`commands/circuit.rs`（IPC）、`src/CircuitPanel.tsx`（前端）。

## 3. 裁决三：熔断时长可配置

### 问题

熔断时长写死 60s（`OPEN_DURATION_SECS` 常量）。不同上游的恢复节奏不一样：有的几秒就好，有的要挂几分钟；60s 对谁都不一定合适，而用户没有调整余地。

### 方案

熔断时长改为**运行期可调**，默认 **60s**、**最小单位 1 秒**：

- 设置存 `app_setting` 表（键 `circuit_open_secs`），启动时读回；
- 保存后**立即生效**（作用于之后新打开的熔断，不追溯修改已在冷却中的熔断）；
- 小于 1 秒的值被钳到 1 秒（最小单位就是 1 秒）。

**只调"连续失败触发的熔断时长"**，不动 429 冷却——429 冷却跟上游的 `Retry-After` 走，指数退避只作下限；用同一个旋钮去覆盖它会破坏"遵守 Retry-After"这条口径。UI 文案里明确写了这一点。

### 取舍

| 选择 | 理由 |
|---|---|
| 存 `app_setting` 键值表，而不是加一列到 `circuit_state` | 设置是"全局参数"，不是"每个渠道的状态"；键值表留给后续设置（T8/T9 可能还要加别的） |
| 存的是**秒的整数** | 最小单位 1 秒，符合"手动调整"的诉求；不做毫秒级 UI |
| 只影响之后的熔断 | 已开始的冷却中途缩短/延长会让"剩余秒数"与实际对不上；用户要立刻生效可以点"解除"再手动触发 |
| 值在写入前先钳到下限 | 保证库里存的值与运行时一致，不会出现"库写 0、运行时按 1"的偏差 |

### 落点

02 §2.3 / §9；实现见 `store/settings.rs`、`store/schema.rs`（`app_setting` + v6 迁移）、`gateway/circuit.rs`（`set_open_duration_secs`）、`commands/circuit.rs`（`circuit_settings_get` / `circuit_settings_set`）、`src/CircuitPanel.tsx`。

## 4. 裁决四：手动解除熔断

### 问题

熔断最长 60s（现在可调）。上游其实已经恢复、但用户不想干等这几十秒时，只能干等。

### 方案

熔断面板每条记录带"解除"按钮 → `circuit_reset(channel_id, upstream_model)`：清掉内存状态**并**删除落库行（重启不会复活）。返回布尔值表示"确实解除了一个熔断"（对健康渠道调用返回 false）。

### 取舍

- **必须同时删落库行**：只清内存的话，重启后落库行会把熔断恢复回来，用户以为解除了其实没有。
- **按 `(channel, upstream_model)` 粒度**：与熔断粒度一致，不做"一键解除全部"——全量解除会掩盖真实故障。
- **不记录解除审计**：v1 不做操作日志；usage_log 属 T7。

### 落点

02 §2.3；实现见 `commands/circuit.rs`（`circuit_reset`）、`gateway/circuit.rs`（`reset` 同时清内存与落库行）、`src/CircuitPanel.tsx`。

## 5. 裁决五：429 冷却上限可配置

### 问题

裁决三把"连续失败熔断时长"做成了可调旋钮，但**429 冷却时长**仍写死成"跟随上游 `Retry-After`，指数退避 60s 封顶"。两个后果：

1. **上游要等很久时，客户端被长时间挡在门外**。上游 `Retry-After: 300`（5 分钟）时，网关会老实等 5 分钟——这在"上游确实被限流"时是对的，但很多上游的 `Retry-After` 是保守值/共享额度值，实际早已恢复。
2. **与已落地的旋钮不一致**：面板上已经有一个"熔断时长"输入框，用户会自然期待 429 的时长也能调。

### 方案

新增**用户可配的 429 冷却上限**，默认 **60s**、**最小单位 1 秒**，存 `app_setting` 表（键 `rate_limit_cooldown_cap_secs`），启动时读回，保存后立即生效。

冷却时长公式（02 §2.3 / §4.4）：

```
冷却 = min(max(指数退避, 上游 Retry-After), 用户上限)
```

- **指数退避的封顶也用这个上限**——一个旋钮管住 429 冷却的全部时长，不留"半可配"的口子。
- **回给客户端的 `Retry-After` 是实际生效的冷却秒数**，不是上游原始值。否则客户端会照着上游的 300s 去等，而网关实际只挡了 60s——两边对不上。

### 取舍

| 选择 | 理由 |
|---|---|
| 上限**可以缩短**上游要求的等待 | 这是用户显式选择的结果——上限调大就能完全尊重 `Retry-After`，调小则换取更短的阻塞。代价是可能更频繁地撞上游限流（甚至触发上游更严厉的封禁），UI 文案里明说了这一点 |
| 默认值 60s（不是"无上限"） | 默认就截断上游较长的 `Retry-After`（上游要 300s → 实际等 60s）。这是有意选的默认：绝大多数本地网关场景下"最多等一分钟"比"可能等五分钟"更可用；真需要完整尊重上游时把上限调大即可 |
| 退避封顶与最终冷却共用同一个上限 | 两套数字会让用户困惑"我设的到底是哪个"；一个旋钮 = 一个语义 |
| 上限**不追溯**已在冷却中的冷却 | 与裁决三的口径一致：改动只作用于之后新触发的冷却；用户想立刻生效点"解除" |
| 上限**不作用于**连续失败熔断时长 | 那是另一个旋钮（`circuit_open_secs`），语义不同（"上游坏了" vs "上游忙了"） |

### 落点

02 §2.3 / §4.4 / §9；实现见 `store/settings.rs`（新键）、`gateway/circuit.rs`（`rate_limit_cap_secs` / `set_rate_limit_cap_secs` / `on_rate_limited` 返回生效值）、`gateway/fallback.rs`（用生效值填错误信息与 `Retry-After`）、`commands/circuit.rs`（`circuit_settings_get` / `circuit_settings_set` 扩为两个参数）、`src/CircuitPanel.tsx`（第二个输入框）。

## 6. 遗留

- **手动解除熔断**：已实现（裁决四）。
- **熔断状态的长期趋势**：未做（只存"当前状态"，不存历史）。要做历史需另立表，属 T13 用量统计的范围。
- **账号级熔断**：粒度仍是 `(channel_id, upstream_model)`，不是 `(channel, account)`——账号池尚未落地（T8/T9）。
- **429 冷却上限已可配**（裁决五）：默认 60s、最小 1s。
- **上游 `Retry-After` 的 HTTP-date 形式**：仍不支持（只认秒数形式），见 `gateway/outbound.rs::parse_retry_after`；解析不了时退化为纯指数退避。
